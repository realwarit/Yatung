## 3. การปิดข้อมูลส่วนตัว 2 ชั้น (AI + server)

ข้อมูลที่เก็บถาวร (`prescriptions.ocr_text`, `llm_json`) ต้องไม่มีข้อมูลระบุตัวผู้ป่วย:

| ข้อมูล | ป้าย | ชั้นที่ 1: AI (prompt สั่งตอนถอดข้อความ) | ชั้นที่ 2: server (`redactPii` ใน `lib/validate-llm-output.js`) |
|---|---|---|---|
| ชื่อผู้ป่วย | `[ชื่อผู้ป่วย]` | ✔ | – (ทำด้วย regex ไม่ได้อย่างน่าเชื่อถือ) |
| HN / AN / VN | `[HN]` | ✔ (หลังเน้นใน prompt) | ✔ regex ป้าย+ตัวเลข |
| เลขบัตรประชาชน 13 หลัก | `[เลขบัตร]` | ✔ | ✔ regex (มีหรือไม่มีขีด) |
| เบอร์โทร | `[เบอร์โทร]` | ✔ | ✔ regex (มือถือ/เบอร์บ้าน/+66) |

**หลักฐานว่าต้องมี 2 ชั้น:** ในการเรียกจริงครั้งแรก Gemini ปิดชื่อผู้ป่วยแต่ **ปล่อย `HN: 123456` ไว้** และ DB เก็บ HN ลงไป — จึงเพิ่มชั้น server และเน้นใน prompt ("แทนทั้งป้ายและตัวเลข") หลังแก้ ตรวจ `ocr_text` และ `llm_json` ของ **ทุกแถวที่สร้าง (9 แถว: 7 เคสของรุ่นหลัก + 2 เคสของรุ่นสำรอง) ✔ ไม่มีชื่อสมมติ, HN, เลขบัตร หรือเบอร์โทร** (รูป 3 มีเบอร์ `081-234-5678` และ HN ด้วย) ส่วนชื่อยา/ชื่อโรงพยาบาลไม่ถูกแทน

ข้อควรรู้ (ระบุใน README หัวข้อ "ความเป็นส่วนตัวของข้อมูล"): รูปต้นฉบับยังถูกส่งให้ Gemini ตามที่พิมพ์บนซอง; เก็บรูปไม่เกิน 7 วัน (cron 03:00 + ลบทันทีเมื่อ confirm/discard ในวันที่ 5)

## 4. ปัญหา 400 และวิธีหาสาเหตุแบบแบ่งครึ่ง

อาการ: Gemini ตอบ `400 INVALID_ARGUMENT "Request contains an invalid argument."` โดยไม่ระบุ field ทั้งรูปและข้อความล้วน (key ใช้ได้ และรุ่นมีอยู่จริง ตรวจด้วย models.list)

วิธี: ใช้ข้อความล้วนกับ `gemini-3.5-flash-lite` เพิ่มทีละส่วนจน 400 แล้วแบ่งครึ่งหา keyword

| ขั้น | ส่งอะไร | HTTP |
|---|---|---|
| 1 | contents ข้อความเดียว | 200 |
| 2 | + `systemInstruction` | 200 |
| 3 | + `responseMimeType: application/json` | 200 |
| 4d | + `responseJsonSchema` ขนาดเล็กสุด (field เดียว) | 200 |
| 4a / 4b | + schema ต้นฉบับเต็ม (4b = inline `$defs`) | **400** |
| 4c | schema เต็ม ตัด keyword ตรวจค่า + description | 400 |
| 4e | 4c + เอา `"null"` ออกจาก `type` | 400 |
| 4f1 | ตัด property `medications` ทั้งก้อน | 200 → ปัญหาอยู่ใน `medications` |
| 4f2 | schema เต็ม ตัด `enum/minimum/maximum/maxItems` | 200 → ปัญหาอยู่ใน 4 keyword นี้ |
| 4g1 / 4g2 | เก็บ `enum`+`maxItems` / เก็บ `minimum`+`maximum` | **400** / 200 |
| 4h1 / 4h2 | เก็บ `maxItems` ตัด `enum` / เก็บ `enum` ตัด `maxItems` | **400** / 200 |
| 4i | **schema ต้นฉบับ inline ตัดแค่ `maxItems`** | **200 ✔** |

**สาเหตุ: `maxItems`** — วิธีแก้: ส่ง `responseJsonSchema` (JSON Schema ต้นฉบับ inline `$defs`) โดยตัด `maxItems` เฉพาะสำเนาที่ส่ง Gemini; Ajv ฝั่งเรายังบังคับ `maxItems` จากไฟล์ต้นฉบับ `enum`, `minimum/maximum`, `minLength/maxLength`, `additionalProperties`, `type: ["string","null"]` ใช้ได้ปกติ (`responseSchema` แบบ OpenAPI subset ก็ 400 เพราะมี `maxItems` เหมือนกัน)

บทเรียน: เพิ่ม log error body ฉบับเต็ม (`gemini error <status>: {…}`) ซึ่งภายหลังช่วยให้เห็นเหตุผลของ 400 ที่ 2 (thinking level) ได้ทันที

## 5. ปัญหาช้าจาก thinking และวิธีแก้

อาการหลังแก้ 400: รูป 1 ผ่านใน 16 วินาที แต่ **รูป 2 (ยาเมื่อมีอาการ) ค้างทุกครั้ง** — timeout 20 วินาทีสองรอบ, curl ค้างเกิน 90 วินาที, streaming 60 วินาทีไม่ได้ข้อมูลเลย, อีกรอบใช้เกิน 4 นาที ขณะที่ข้อความสั้นทั่วไปใช้ 4 วินาที (API ไม่ได้ล่ม)

| การทดลอง (ข้อความ Paracetamol "1–2 เม็ด ทุก 4–6 ชม." + schema เต็ม) | เวลา |
|---|---|
| thinking ค่าเริ่มต้น | **32 วินาที** |
| `thinkingConfig.thinkingLevel: "minimal"` | **10 วินาที** (ผลถูกเท่ากัน) |

**วิธีแก้:** ตั้ง `thinkingLevel` ตามรุ่น (`scanService.thinkingLevelFor`): ชื่อรุ่นมี `lite` = `minimal` (รวม `gemini-3.1-flash-lite` ที่ทดสอบแล้วรับได้), รุ่นอื่น = `low` (เพราะ `gemini-3.8-flash` ตอบ 400 "Thinking level MINIMAL is not supported for this model") + เพิ่ม `maxOutputTokens: 4096` (ถ้า `finishReason = MAX_TOKENS` ตอบ 422 `AI_NO_RESULT` ไม่ retry) + เพิ่มกฎใน prompt: ค่ากำกวม ("1–2 เม็ด", "ทุก 4–6 ชม.") ให้ใช้ค่าน้อยสุด ลด confidence ≤ 0.5 และบันทึกใน `unreadable_parts` ทันที ห้ามคิดวนหาคำตอบที่ถูกที่สุด
ผล: ทุกเคสของตัวหลักใช้ **3–4 วินาที** (จาก 16 วินาทีถึงค้างเกิน 4 นาที)

## 6. การสลับรุ่นและงบเวลารวม 40 วินาที

- งบเวลารวมต่อคำขอ **≤ 40 วินาที** (รวมลองซ้ำ/สลับรุ่น): ครั้งแรก timeout 20 วินาที ครั้งถัดไปใช้เวลาที่เหลือ เหลือไม่ถึง 8 วินาทีไม่ลองใหม่ → 503 `AI_UNAVAILABLE` · frontend timeout 50 วินาที
- **429 / 503 / timeout ที่รุ่นหลัก → สลับไปรุ่นสำรองทันที** (คนละรุ่นกัน ไม่หน่วง) ถ้าไม่มีรุ่นสำรองที่ต่างรุ่น: 503/timeout ลองรุ่นเดิมหลังเว้น 2 วินาที · 4xx อื่นไม่ retry · งบ retry 1 ครั้งต่อคำขอ · `llm_model` ใน DB บันทึกรุ่นที่ใช้จริง
- ทดสอบ flow จริงกับ Gemini ปลอม (`scripts/fake-gemini.js` ตอบตามชื่อรุ่น และตอบ 400 ถ้า body มี `maxItems`/`temperature`/ไม่มี `maxOutputTokens=4096`/`thinkingLevel` ไม่ตรงรุ่น): ปกติ, 429→สลับรุ่น, 503→สลับรุ่น, 503 ไม่มีรุ่นสำรองต่างรุ่น→ลองรุ่นเดิมหลัง 2 วินาที, 503 ทั้งสองรุ่น→503 (ยิง 2 ครั้ง), 400→ไม่ retry, คำตอบถูกตัด→422, ช้า→สลับรุ่นหลัง 20 วินาที, ช้าทั้งสองครั้ง→**503 ที่ 40 วินาที** (ยิง 2 ครั้ง), API key ไม่ถูก log
- บั๊กที่เจอจากการทดสอบนี้: node `http request` เมื่อ timeout ส่ง msg ทั้งทาง catch และ output ทำให้ตัดสินซ้ำสองรอบ — แก้โดยไม่ใช้ catch node และถือ `statusCode` ที่ไม่ใช่ตัวเลขเป็น error

## 7. โควตาที่ใช้ และข้อสรุปสำหรับวันนำเสนอ

| รุ่น | จำนวน request ที่ยิงจริง | หมายเหตุ |
|---|---|---|
| `gemini-3.5-flash-lite` | ~31 | วินิจฉัย 400 และช้า ~24, ชุดทดสอบ 7 เคส |
| `gemini-3.1-flash-lite` | 2 | ยืนยันรุ่นสำรอง (รูป 1 และ 2) |
| `gemini-3.8-flash` | 4 | 2 ครั้งแรก 400 (minimal ไม่รองรับ), 2 ครั้งหลัง 503 "high demand" (ใช้เกินเพดาน 3 ไป 1 ครั้งเพราะ backend ลองซ้ำเอง) — **ไม่เคยได้ผลสำเร็จ จึงไม่ใช้และไม่ทดสอบเพิ่ม** |

**คำแนะนำ:** ใช้ `gemini-3.5-flash-lite` เป็นตัวหลัก (เร็ว 3–4 วินาที ถูกทุกเคส) และ `gemini-3.1-flash-lite` เป็นตัวสำรอง (11–12 วินาที ถูกทั้งสองเคสที่ทดสอบ) สำรองสุดท้ายสำหรับวันนำเสนอคือ `AI_MOCK=true`

## 8. ข้อจำกัดที่ยังมี

- ผลของ Lite รูป 2 มีคำพิมพ์ผิดเล็กน้อยใน `unreadable_parts` ("ขนาดยเป็นช่วง") — เป็นข้อความที่โมเดลเขียนเอง ไม่กระทบค่า
- `dose_per_time` ของยาแบบช่วง ("1–2 เม็ด") ถูกตั้งเป็น 1 (ค่าน้อยสุด) พร้อม flag ให้ผู้ใช้ตรวจ — ตั้งใจให้ปลอดภัยไว้ก่อน
- ทดสอบกับรูปจำลองที่พิมพ์ด้วยเครื่อง 5 รูปและข้อความ 2 แบบ ยังไม่ได้ทดสอบกับถ่ายซองจริงหลายแบบ/ลายมือ (นอกสโคป)
- ผลลัพธ์ของ AI เป็นข้อมูลช่วยเท่านั้น ผู้ใช้ต้องตรวจในหน้า Review ทุกครั้ง · ไม่ใช่คำแนะนำทางการแพทย์
